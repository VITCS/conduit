⚡ Technical Design Document

Conduit — an open-source AI software factory.

Conduit turns a ticket into a reviewed pull request: agents triage, plan, code and CI-verify the change, with human approval gates, on a visual workflow graph. This document describes the system's architecture, stack, data model, execution engine, end-to-end flows and the engineering decisions behind them.

Status Beta Backend Go 1.24 UI Next.js 16 · React 18 Deploy Single binary License Open source

01Introduction

What Conduit is, who it's for, and the one idea the whole system is built around.

Conduit is a control plane for AI-assisted software delivery. A ticket enters from Jira, Notion, GitHub, a webhook or the board; a chain of components — some of them LLM agents — refine it into a plan, write the code on a branch, verify it against CI, and open a pull request. Crucially, nothing risky happens without a human: the pipeline pauses at explicit approval gates, and a pull request flows on to a review workflow that a person triggers.

The organising idea is that an automation is a graph, not a script. Every workflow is a directed graph of typed components (nodes) connected by labelled edges. An engine walks the graph, runs each component, and follows the edge whose label matches the component's outcome (success / failed / approved). This makes the behaviour visible, versioned, pausable and re-runnable — the opposite of a one-shot prompt.

Visible

Runs stream live over SSE onto a React-Flow canvas; every node shows its state, output and logs.

Gated

Two human approval gates per ticket (plan, then exact file changes). CI must pass before a PR opens.

Self-hosted

One Go binary with an embedded UI. Your models, your keys, your CI. Postgres or in-memory store.

02Goals & scope

Goals

  • Automate routine engineering tickets end-to-end, from source to reviewed PR.
  • Keep a human in the loop at the moments that matter, with full context at each gate.
  • Make every run observable and reproducible — live canvas, logs, memory, re-run.
  • Be model- and vendor-agnostic: Anthropic, OpenAI, or a self-hosted gateway.
  • Ship as a single self-hostable binary with no mandatory external services.
  • Treat workflows as versioned data that can be edited, bypassed and upgraded safely.

Non-goals

  • Not an autonomous agent that acts without gates — orchestration is deterministic.
  • Not tied to one LLM provider or one source tracker.
  • Not a hosted SaaS; multi-tenancy is project-scoped within one deployment.
  • Not a replacement for code review — it feeds review, it doesn't skip it.
Design tenet. Components are simulated by default (deterministic, offline) so the product demos and tests run with no provider or credentials; a node opts in to real side effects with live:true and a secret.

LLM calls are plain HTTPS through a long-timeout, SSRF-guarded client. There is no agent framework (no LangChain / LlamaIndex): orchestration is Conduit's own deterministic DAG engine; the "agent" is a node that renders a templated prompt and calls a provider.

Stdlib-first Go

Fewer dependencies = a smaller attack surface, trivial cross-compilation, and a binary that starts instantly. The mux, SSE and JSON needs are modest and well-served by stdlib.

Embedded static UI

Exporting Next.js to static files and embedding them means one artifact to ship and no separate web server, CORS or build coupling at runtime.

React Flow

The product is a graph; React Flow gives pan/zoom, nodes, edges and handles for free, so effort goes into the domain (components, live state) not canvas plumbing.

Pluggable store

One Store interface with in-memory & Postgres implementations keeps tests fast and offline while production gets durability and multi-instance workers.

06Execution engine

The engine is a parallel, cancellable DAG scheduler with bounded recovery loops, human gates, and a worker-claim model for horizontal scale.

How a run executes

  1. Enqueue. A run is created with every step pending and status queued. (EnqueueForTask seeds a board task's ticket into run memory.)
  2. Claim. A worker atomically leases a claimable run (queued, or a crashed run whose lease expired) and calls ExecuteClaimed, renewing the lease while it runs.
  3. Walk. The scheduler activates the trigger nodes (or resume_from on a re-run). Each node runs once, in its own goroutine; independent branches run concurrently.
  4. Route. After a node returns an outcome, the engine follows every outgoing edge whose label matches (success/failed/approved/unlabelled).
  5. Gate. An approval node sets the run waiting, renders the agent's suggestion as the gate summary, and blocks until a human resolves it (or the context cancels).
  6. Recover. A failing node with a retry back-edge (max_attempts) re-enters the loop body carrying its failure context in memory, up to budget — then routes terminally.
  7. Finalize. Unreached nodes are skipped; the run is marked terminal; a bound task's board stage is projected (Done / Blocked), and a freshly opened PR is handed to the review inbox.

Key mechanisms

Bypass (skip)

A node flagged disabled is not executed — marked skipped, the run continues down its success edges. Used to make an optional step (e.g. CI) opt-in.

Cancellation

Cancel cancels the run's context. The scheduler checks ctx.Err() after every node, so a cancel breaks even a recovery loop and the run finalizes promptly.

Re-run from a node

Rerun(runID,nodeID) resets that node and its descendants to pending, keeps upstream results & memory, and re-queues with resume_from set.

Live status

Each node broadcasts a step.updated(running) as it starts, so the UI shows "in progress" without a refresh.

// the scheduler's core loop (simplified)
activate(id):
  outcome = runNode(ctx, id)
  if outcome == canceled or ctx.Err(): stop branch
  if outcome == failed and tryRetry(back-edge budget): re-enter loop
  for edge in out[id]:
    if edge.label matches outcome: activate(edge.to)

09AI approach & framework

Conduit is "agentic" at the level of the graph, not an autonomous loop. The intelligence lives in a few well-scoped LLM nodes with human gates around them.

No agent framework — on purpose

There is no LangChain, no tool-calling autonomy loop. An "agent" node renders a templated prompt and calls a provider over HTTPS; the orchestration is Conduit's deterministic DAG. This keeps behaviour inspectable, versioned and gate-able.

Prompt templating

Config values resolve four reference kinds before a call:

  • ${input.x} — the triggering payload (dotted paths into a webhook body).
  • ${memory.x} — shared run state written by earlier steps.
  • ${var:x} — project configuration variables.
  • ${secret:x} — encrypted project secrets (API keys, tokens).

The AI Factory pipeline

  1. Triage — score a ticket's readiness (confidence); low scores route to a human, not the agent.
  2. Refine & plan — an agent turns the ticket into a plan.
  3. Human gate ① — approve the plan.
  4. Plan changes — produce a file-level change plan.
  5. Human gate ② — approve the exact files.
  6. Apply — write each file and push a branch via the GitHub Git Data API.
  7. Verify CI — gate on real check-runs; on failure, loop back with the errors.
  8. Open PR → hand off to the review workflow.
Coding strategy. The apply step requests one file per model call (raw content, no JSON array). This avoids truncation: only a single file must fit in any one response, so multi-file changes scale and a cut-off is detected (stop_reason:max_tokens) rather than silently corrupting output.

Confidence as a routing signal

Triage emits a confidence score; the workflow edges route success (ready) vs failed (needs clarification). Automation is applied only where the work is scoped and checkable — the rest waits for a person. This is the core safety idea: don't automate what you can't verify.

10Security

AuthN

Email + bcrypt, JWT sessions, and optional Google/GitHub OAuth with a self-hosted identities layer. A bootstrap admin is seeded on first run.

AuthZ

Project-scoped membership with roles (owner/admin/member/viewer). Writes are gated by effective role; built-in projects can't be deleted.

Secrets

Project secrets are encrypted at rest with CONDUIT_SECRET_KEY and only resolved at execution via ${secret:…} — never returned to the client.

SSRF guard

Outbound HTTP from components goes through a guarded client; private/loopback egress is denied unless explicitly allowed (CONDUIT_ALLOW_PRIVATE_EGRESS).

Transport hardening

Middleware chain: security headers → body-size limit → rate limit → auth → project scope. The SSE token rides as a one-endpoint query param (EventSource can't set headers).

Audit

Config changes are recorded; GET /api/audit exposes the trail.

13Testing strategy

Go unit tests

Per package — engine (DAG, gates, retries, cancel, rerun, bypass, handoff), components (LLM adapters via httptest, GitHub Git Data stubs, truncation), store (cascade, claim), api (handlers).

Playwright e2e

Real UI against the real server: landing → auth → run → live SSE → approval, and account creation.

Offline by default

Simulated components and the in-memory store mean the whole suite runs with no provider, no DB and no network.

14Engineering learnings

Decisions and fixes that shaped the system — the "why it is the way it is".

Make every step simulated-by-default product›
Each component returns a deterministic result unless live:true. The seeded factory, the demos and the whole test suite run offline. Real side effects are an explicit opt-in with a secret — which also means a safe, credential-free first-run experience.
Expand ${var}/${secret} everywhere, not just prompts bug›
An agent node read provider/model raw, so ${var:llm_model} reached the API verbatim (a confusing 404). Fix: route every field through the same expansion, and fail fast with guidance when a reference is unresolved instead of calling the provider with a literal token.
One file per model call beats one big JSON array AI›
Asking for all changed files as a single JSON array truncated at the token cap. Implementing one file per request (raw content) means only a single file must fit any response; truncation is detected (stop_reason:max_tokens) rather than corrupting output.
Diagnose GitHub 404s instead of blaming the branch DX›
A 404 on git/ref/heads/main is usually a wrong owner/repo or a token that can't see a private repo — not a missing branch. The code now probes the repo and returns an actionable message, and normalizes owner/repo (full URLs, owner/repo, trailing .git).
Cancel must break the recovery loop engine›
Components do network I/O that doesn't observe the run context, so a node could return failed after a cancel and the retry back-edge would re-queue forever. The scheduler now checks ctx.Err() after each node, so cancel ends the run promptly.
Upgrade built-ins without clobbering edits ops›
Seeding keyed only by ID froze old definitions on existing databases. Workflows now carry a rev and a content seed_hash; startup upgrades an unedited built-in to the shipped revision and leaves a user-edited one alone.
Broadcast the running transition for live UI UX›
A node only logged when it started, so the canvas never showed "in progress" until a refresh. Emitting a step.updated(running) as each node begins makes progress visible live over SSE.
A per-node bypass toggle for optional steps product›
Not every environment can run every step (e.g. a token that can't read the Checks API). A disabled flag skips a node and continues down its success edges, and the toggle persists immediately so it applies to the next run.
Hand opened PRs to a review pipeline feature›
When a run opens a PR, the engine records a pending review request in the GitHub project's inbox (never self-reviewing). A person triggers the review workflow from a banner — keeping the human in the loop across the whole lifecycle.
